写给忙碌后回来、需要快速找回上下文的你。下面用三分钟把「项目是什么、Java 后端做了什么、这条分支在改什么」讲清楚。

① 项目全貌

InterviewMentorAI 是一个「AI 面试评估」SaaS 平台，一仓三端：

  • frontend_flutter — Flutter 客户端（候选人答题、HR 查看报告）。
  • backend_springai — 本次评审对象。Spring Boot 业务后端：多租户、鉴权、面试记录、报告、知识库 CRUD，负责编排。
  • backend_python — AI 引擎。跑 RAG 检索 + 多 Agent 评估流水线 + LLM 接入，通过 HTTP 暴露 :8000。

数据流是：Flutter 上传音频/答案 → Spring 落库并触发分析 → 调 Python 做转写+RAG+多 Agent 打分 → 结果回写成面试报告 → HR 可人工修正。

② Python 侧刚刚发生了什么（这是理解本分支的关键背景）

最近两个提交把 backend_python 做了彻底重构：RAG 拆成 Chunking / Embedding / Reranker 三个独立服务，评估流水线改 asyncio.gather 并发，配置迁到 Pydantic，统一异常体系，测试从 78 涨到 103 个全绿。Python 端已经是一套标准的 RAG 分层模型。

③ 这条分支 feature/arch-core 正在做的事

提交历史显示 Java 侧刚从一个电商脚手架（com.ecommerce）改造成面试平台（com.interview.mentor），并升级到 Java 17 / SB 3.2.5 的企业级多租户底座。当前这批未提交的暂存改动，方向是「让 Java 业务模型向 Python 的 RAG 能力对齐」：

  • 给 InterviewRecord / t_interview 加 userId、jobRole — 让面试记录能标记候选人与岗位，喂给 Python 做针对性评估。
  • 新增 t_knowledge_document 表 + KnowledgeDocument 实体 + Mapper，带 embedding_status 字段 — 为知识库文档接入向量化流程铺路。
  • 把 TenantInfo 从 record 改回普通类、修正报告分页构造 — 一些兼容性/稳健性修补。
  • 把测试包从 com.ecommerce.backend_springai 迁到 com.interview.mentor，删掉遗留的 RecordControllerTest。

④ 一句话结论：你正处在「架构调整阶段」的哪个点

你在 搭建阶段的收尾期：多租户 + 鉴权 + RAG 知识库的骨架已铺开，但骨架里塞了两套互相矛盾的设计残留，且几个核心机制处于「声明了但没接通」的半成品状态。这正是做架构深化最划算的时机——先把浅模块与死代码收敛、把没接通的接缝接通，再往上加功能。下面 5 张卡片就是本轮找到的深化机会，按「删除测试」与「深模块」原则排序。

B · 收敛知识库的两套并存设计

entity/{KnowledgeBase,KnowledgeDoc,KnowledgeChunk,KnowledgeDocument}.java · mapper/{KnowledgeDoc,KnowledgeDocument,KnowledgeBase}Mapper.java

Before — 四实体，三个是孤儿

KnowledgeDocument Controller→Service→Mapper 全链路
KnowledgeBase 仅 Mapper，零业务引用
KnowledgeDoc 仅 Mapper，零业务引用
KnowledgeChunk 连 Mapper 都没有

两套互斥模型并存：扁平文档（Document）vs RAG 三层（Base→Doc→Chunk）。RAG 那套一行业务都没写。

路线甲（快）：只保留 KnowledgeDocument，删 3 实体 + 2 Mapper。纯复杂度净减。
路线乙（对齐 Python）：围绕 RAG 三层建深模块，废弃扁平 Document，与 backend_python 的 Chunking/Embedding 对齐。

删除测试：删任一套都收敛复杂度，不转移 — 信号明确。

问题 — 4 实体只有 1 个接线，其余是死代码，且分属两种互斥领域设计。

方案 — 依产品方向选一套：仅扁平文档就删 RAG 三层；要接 Python RAG 就删扁平 Document 并建三层深模块。

  • 删 3 实体 + 2 Mapper
  • 复杂度净减不转移
  • 与 Python RAG 对齐

C · 把「租户隔离」沉成一个深模块

tenant/{TenantContext,TenantFilter,TenantService}.java · security/JwtTokenProvider.java · 各 ServiceImpl 手写 .eq(tenantId)

Before — 两套范式碎片 + 三处断线

TenantFilter 解析 schemaName…
…但没有任何 schema 切换消费它
JWT 不含 tenant，靠可伪造的 X-Tenant-ID header
Filter 顺序早于 Security，JWT 路径恒失效
每个 Service 手写 .eq(tenantId)，易漏（见候选 A）

After — 一层拦截，业务无感

JWT 携带 tenantId claim
+ TenantLineInnerInterceptor 自动注入
↓ 租户过滤对 Service 完全不可见 ↓
Service 只写业务，不再手写 .eq(tenantId)

删除 schemaName 全部残留，选定共享 schema 行级隔离一种范式。

问题 — schema 隔离声明与 tenant_id 行级实现并存且都没做对，租户身份可被 header 伪造。

方案 — JWT 写入 tenantId，用 MyBatis-Plus 拦截器自动注入租户条件，租户隔离沉为深模块。

  • leverage：一处拦截，N 个查询
  • 消除手写过滤遗漏
  • 堵住 header 伪造越权

Top recommendation · 先动哪一个

从候选 A + C 一起开刀：租户隔离

候选 A（报告跨租户泄漏）是最直接的安全缺口，改动小、收益立即，必须先堵。而它的根因正是候选 C——各 Service 手写 .eq(tenantId) 必然会漏。把租户隔离沉成一个深模块（JWT claim + MyBatis-Plus 拦截器），A 会作为 C 的第一个受益点自然被修复，之后再没有下一处遗漏。候选 B 是投入产出比最高的「删除测试」一刀，紧随其后作为清理；D、E 属于把半成品接缝接通，等隔离稳固后自然浮现为下一批。
