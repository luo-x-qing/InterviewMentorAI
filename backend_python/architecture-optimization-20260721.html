前言：Python 后端现状

项目定位

InterviewMentorAI 是一个 AI 驱动的模拟面试复盘助手，采用 Java + Python 双后端架构。 Java 后端负责业务交付（用户管理、面试记录、数据持久化），Python 后端专责 AI 能力： 语音识别、说话人分离、RAG 检索增强、智能评估、报告生成。

Python 后端已实现完整的 5 步 Agent 流水线，从音频输入到结构化报告输出， 并通过 RAG 系统接入面试知识库，减少大模型幻觉，提升评估准确性。

核心方法与技术

RAG 检索策略

  • • 向量检索：DashScope text-embedding-v3 + cosine similarity
  • • 关键词检索：jieba 分词 + BM25 算法（k1=1.5, b=0.75）
  • • 混合检索：向量 70% + BM25 30% 加权融合
  • • 重排序：BAAI/bge-reranker-base Cross-Encoder

文档处理

  • • 固定分块：500 字符，重叠 100 字符（20%）
  • • 段落分块：按双换行符分割，保持语义完整
  • • 语义分块：按句子边界（。！？）切分
  • • 缓存：MD5 哈希缓存 embedding，避免重复调用

架构模式

  • • 依赖注入：FastAPI Depends + app.state
  • • 分层架构：API → 业务 → 基础设施 → 数据
  • • 生命周期管理：lifespan context manager
  • • 延迟加载：reranker 模型按需初始化

质量保障

  • • 单元测试：103 个用例，pytest + pytest-mock
  • • Mock 策略：外部 API 全部 mock，本地可运行
  • • 日志：结构化日志，便于调试追踪
  • • 错误处理：降级兜底（_fallback_dialogue_parse）

问题：RagService 承载了 6 种职责（分块 ×3、向量化、缓存管理、重排序、检索、入库），interface 几乎等同于 implementation，是典型的浅层模块。

解决方案：拆分为 ChunkingService（分块策略）、EmbeddingService（向量化 + 缓存）、RerankerService（重排序），RagService 精简为纯检索入口。

  • • locality：分块逻辑变更只改 ChunkingService
  • • leverage：EmbeddingService 可被知识库导入和在线检索共用
  • • testability：每个模块可独立 mock 测试

  • • leverage：一个配置类，自动处理所有环境变量
  • • testability：可直接实例化 Settings() 进行测试
  • • locality：配置逻辑集中在一处，移除 17 行手写代码

流水线异步化

✓ 已完成
backend_python/app/services/agent_pipeline.py (246行 → 247行)
→ _evaluate_answers() 改为 asyncio.gather 并发评估

Before — 串行评估

评估问答 1
↓ await 2s
评估问答 2
↓ await 2s
N 个问答: N × 2s

After — 异步并发

评估 1
评估 2
评估 N
↓ asyncio.gather 并发
总耗时: ~2s（与 N 无关）

问题：_evaluate_answers() 串行 await 每个评估，N 个问答对总耗时 N × 单个 LLM 延迟（约 2s）。

解决方案：使用 asyncio.gather 并发发起所有 LLM 评估调用，总耗时降至单个 LLM 调用延迟（约 2s）。

  • • leverage：N 个评估从 N×2s 降至 ~2s
  • • scalability：问答对越多，收益越大
  • • compatibility：与 FastAPI async 生态对齐

✓ 已完成
backend_python/app/core/exceptions.py (+140行)
backend_python/app/services/*.py + backend_python/app/api/*.py (统一异常类型)

Before — 混乱异常

raise Exception("文档入库失败")
raise Exception("向量化失败")
raise Exception("千问调用失败")
# 全是 generic Exception
# 无法区分错误类型

After — 结构化异常

class AppError(Exception): ...
class LlmError(AppError): ...
class LlmTimeoutError(LlmError): ...
class LlmRateLimitError(LlmError): ...
class VectorDbError(AppError): ...
class EmbeddingError(AppError): ...
# 精确捕获，分层处理

问题：所有服务层都抛出 generic Exception，调用方无法区分错误类型，无法做针对性重试或降级。

解决方案：定义异常层次结构（AppError → LlmError / VectorDbError / EmbeddingError / ChunkingError / KnowledgeError / PipelineError），API 层根据异常类型返回不同 HTTP 状态码。

  • • locality：异常定义集中在 exceptions.py
  • • leverage：一个 except LlmError 可捕获所有 LLM 相关错误
  • • testability：24 个异常测试用例，覆盖继承关系和 HTTP 状态码映射

执行记录：流水线异步化

2026-07-21 — 消除候选方案 4

执行背景

项目已使用 AsyncOpenAI（异步客户端），所有服务层方法均为 async def。 但 _evaluate_answers() 方法中，对 _evaluate_single() 的调用是串行 await—— 每个问答对必须等待前一个 LLM 调用完成才能开始。N 个问答对的总耗时 = N × 单个 LLM 延迟（约 2s）。

codebase-design 词汇应用

Module
AgentPipeline._evaluate_answers()
Interface
方法签名不变，无调用方感知
Depth
内部实现从串行改为并发，接口不变
Leverage
N 个评估从 N×2s 降至 ~2s

设计决策

D1
gather(return_exceptions=True) 而非 as_completed
使用 return_exceptions=True 确保某个评估异常不会中断其他并发任务。异步任务执行完毕后统一筛选有效结果，保持代码简洁。
D2
LlmClient 无需修改
项目已使用 AsyncOpenAI，LlmClient.call() 本身就是 async 方法。gather 直接并发 await 即可，无需切换 HTTP 客户端。
D3

_evaluate_answers() 方法签名不变，返回值不变。所有调用方（_parse_dialogue → _evaluate_answers → _generate_report 的流水线顺序）无感知。 这是 codebase-design 中 "Depth" 的典型应用：内部实现深化，接口不变。
