SaaS 多租户架构核心概念

学习目标： 理解 SaaS 和多租户的基本原理，掌握三种数据隔离策略，为 InterviewMentorAI 的 Java 后端重构打下基础。

什么是 SaaS？

SaaS（Software as a Service，软件即服务）是一种软件交付模式。简单来说，用户通过互联网使用软件，而不需要在自己的电脑上安装和维护。

想象一下你家里的水电煤：你不需要自己建发电厂或水厂，只需要拧开水龙头就有水，按下开关就有电。SaaS 也是一样——你不需要自己搭建服务器、安装软件，只需要打开浏览器就能使用。

什么是多租户？

多租户（Multi-Tenant）是 SaaS 的核心技术架构。它的意思是：多个用户（租户）共享同一个软件实例，但各自的数据和配置是隔离的。

打个比方：多租户就像一栋公寓楼。所有住户共享大楼的水电煤、电梯、门禁系统，但每户人家有自己独立的房间、锁和生活空间。你不能打开邻居家的门，邻居也不能打开你家的门。

为什么需要多租户？

如果没有多租户，每个客户都需要独立部署一套系统，就像每个人都需要自己建一栋房子。有了多租户，大家可以共享基础设施，成本大大降低。

对比维度 传统模式（每客户一套系统） 多租户模式（共享系统）
成本 高（每个客户都需要服务器、运维） 低（共享基础设施）
维护 复杂（需要维护多套系统） 简单（只需维护一套系统）
升级 困难（需要逐个升级） 简单（一次升级，所有客户生效）
扩展 慢（新客户需要从零开始） 快（新客户可以快速接入）

多租户数据隔离策略

多租户的核心挑战是：如何确保每个租户的数据只能被自己访问，而不能被其他租户或平台管理员随意访问？这就是数据隔离。

想象一下：你住在公寓楼里，你的房间有门锁，你的信件有邮箱，你的快递有取件码。这些就是"隔离"手段。在软件系统中，数据隔离也有三种主要策略：

策略一：独立数据库（Database per Tenant）

每个租户拥有完全独立的数据库实例。

打个比方： 每个租户拥有自己独立的房子，连邻居都没有。

  • 优点： 隔离性最好，安全性最高，备份恢复简单
  • 缺点： 成本最高，维护复杂，跨租户查询困难
  • 适用： 对数据安全要求极高的金融、医疗行业

策略二：共享数据库，独立 Schema（Schema per Tenant）

所有租户共享同一个数据库实例，但每个租户拥有独立的 Schema（数据库模式）。

打个比方： 所有租户住在同一栋楼里，但每户人家有自己独立的房间和门锁。

  • 优点： 隔离性较好，成本适中，维护相对简单
  • 缺点： 跨租户查询需要切换 Schema，性能有一定影响
  • 适用： 中型企业 SaaS，数据安全要求较高

策略三：共享数据库，共享 Schema（Shared Database, Shared Schema）

所有租户共享同一个数据库和 Schema，通过 tenant_id 字段区分数据归属。

打个比方： 所有租户住在同一个大房间里，但每个人有自己的床和柜子，通过名字标签区分。

  • 优点： 成本最低，维护最简单，跨租户查询方便
  • 缺点： 隔离性最差，需要应用层严格控制数据访问
  • 适用： 小型 SaaS，对隔离性要求不高
InterviewMentorAI 的选择： 我们采用策略二：共享数据库，独立 Schema。平台数据（用户、租户、订阅）放在 platform schema，业务数据（面试、评估、报告）放在 tenant_{id} schema。这样既保证了数据隔离，又控制了成本。

多租户架构的核心组件

一个完整的多租户系统通常包含以下核心组件：

1. 租户上下文（Tenant Context）

租户上下文负责在请求处理过程中传递当前租户信息。你可以把它想象成"门禁卡"——每个请求都需要刷卡才能进入，系统通过门禁卡知道你是哪个租户。

// 伪代码示例
public class TenantContext {
    // 使用 ThreadLocal 存储当前租户信息
    private static final ThreadLocal<Long> TENANT_ID = new ThreadLocal<>();
    
    // 设置当前租户
    public static void setTenantId(Long tenantId) {
        TENANT_ID.set(tenantId);
    }
    
    // 获取当前租户
    public static Long getTenantId() {
        return TENANT_ID.get();
    }
    
    // 清除当前租户（请求结束后）
    public static void clear() {
        TENANT_ID.remove();
    }
}

2. 租户解析器（Tenant Resolver）

租户解析器负责从请求中提取租户标识。就像门禁系统需要识别你的门禁卡一样，系统需要知道当前请求属于哪个租户。

常见的解析方式：

  • 请求头： 从 HTTP Header 中读取 X-Tenant-ID
  • JWT Token： 从 JWT claims 中提取 tenantId
  • 子域名： 从 URL 子域名中解析（如 tenant1.app.com）
  • URL 参数： 从请求参数中获取（如 /api/data?tenantId=1）

3. 数据访问层（Data Access Layer）

数据访问层需要根据租户上下文自动切换数据源或 Schema。就像公寓楼的物业系统需要知道你住哪个房间，才能帮你处理你的事务。

4. 权限控制（Permission Control）

多租户系统需要严格的权限控制，确保租户只能访问自己的数据。就像你不能用你的门禁卡打开邻居家的门一样。

InterviewMentorAI 的多租户设计

在 InterviewMentorAI 项目中，我们的多租户设计如下：

数据流示意图

HTTP 请求
  ↓
JwtAuthenticationFilter  → 解析 JWT，提取用户名
  ↓
TenantFilter             → 从 JWT/请求头解析 tenantId
  ↓                         → 查询 schemaName
TenantContext.set()      → ThreadLocal 存储 { tenantId, schemaName }
  ↓
Controller / Service     → 通过 TenantContext.getTenantId() 获取当前租户
  ↓
TenantContext.clear()    → 请求结束，清理 ThreadLocal

关键理解： 多租户的核心是"共享但隔离"——所有租户共享同一个软件实例和基础设施，但每个租户的数据和业务逻辑是完全隔离的。这就像公寓楼里的住户，共享大楼的水电煤，但每户人家有自己独立的房间和门锁。
